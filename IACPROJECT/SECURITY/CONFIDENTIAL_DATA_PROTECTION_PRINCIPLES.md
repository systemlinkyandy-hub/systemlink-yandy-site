# IACProject 機密データ保護原則

**作成日**：2026-08-05  
**対象**：Residual Capacity Workbench / 体調環境ログ / 残コルチゾールHP / 将来のサーバ・クライアント型構成  
**状態**：保存必須・消失禁止・設計前提

---

## 1. 結論

Residual Capacity Workbenchで扱う服薬、症状、身体画像、環境、認知・情動、就労条件などのデータは、単なるアプリデータではなく、機密性の高い個人研究データとして扱う。

完全な侵入防止は保証できない。したがって、次の四点を設計原則とする。

- 盗まれても読めない
- 一部が破られても全体へ到達できない
- 誰が触ったか追跡できる
- 漏えい時の被害範囲を限定できる

暗号化は魔除けではなく、侵入後の被害範囲を設計する技術として扱う。

---

## 2. 必須原則

### 2.1 クライアント側暗号化

機密データは、可能な範囲でサーバ送信前に端末側で暗号化する。

対象例：

- 服薬履歴
- 症状ログ
- 身体画像
- 自由記述
- Reviewer Note
- 認知・情動記録
- 就労・生活条件

暗号方式は独自実装せず、実績のある標準ライブラリを用いる。

### 2.2 データと鍵の分離

暗号化データと復号鍵を同じ場所へ置かない。

想定構成：

- データ本体：暗号化データベース
- データ暗号鍵：暗号化して保存
- 上位鍵：OS安全領域、KMS、Key Vault、HSM等

エンベロープ暗号化を前提候補とする。

### 2.3 本人情報と研究データの分離

氏名、住所、メールアドレス等の本人情報と、服薬・症状・環境・画像等の研究データを分離する。

例：

```text
本人情報DB
氏名等 → Patient ID

研究データDB
Patient ID → 服薬・症状・環境・画像
```

対応表は別系統で暗号化し、研究者やAIには原則としてPatient ID側のみを渡す。

### 2.4 AI入力の最小化

AIへ渡す情報は、解析に必要な範囲へ限定する。

- 対象期間だけ
- 必要項目だけ
- 氏名・住所・連絡先を除去
- 正確な住所を地域・気象区分へ変換
- 画像内の氏名・患者番号を除去
- データベース全体を渡さない
- AI入力用一時データを処理後に削除

機密性の高い処理は、将来的にローカルAIまたは専用環境へ分離する。

### 2.5 役割別アクセス制御

「ログインできるか」だけでなく、「誰が何を見られるか」を役割ごとに分ける。

例：

- 本人：原データ全体
- 内分泌Reviewer：服薬・症状・介入反応
- 身体Reviewer：疼痛・筋緊張・身体画像
- 就労支援：活動余力と勤務条件
- AI：解析に必要な切り出しデータのみ

管理者が常に全データを読める構造は避ける。

### 2.6 監査ログ

最低限、次を記録する。

- 誰が
- いつ
- どのデータを
- 閲覧・変更・出力したか
- どのAIモデルへ何を送ったか
- AI結果を誰が採用・不採用にしたか

監査ログは、通常データとは別に保存し、利用者が後から容易に書き換えられない構造とする。

### 2.7 鍵の交換・失効

鍵はソースコード、GitHub、平文設定ファイルへ直接書かない。

必要項目：

- 鍵生成
- 保管
- ローテーション
- 失効
- バックアップ
- 漏えい時の再暗号化

### 2.8 削除可能性

本人が共有を取り消した場合に、次を実行できる構造とする。

- アクセス権停止
- 鍵失効
- サーバ上コピー削除
- AI入力用一時データ削除
- 派生データ・キャッシュ・バックアップの扱い明示

---

## 3. 初期MVPで最低限入れるもの

```text
端末
 ├─ 端末内データ暗号化
 ├─ 通信TLS
 └─ 必要項目だけ送信
          ↓
APIサーバ
 ├─ 認証
 ├─ 役割別権限
 ├─ 監査ログ
 └─ 平文を長時間保持しない
          ↓
暗号化DB
 ├─ 本人情報と研究データを分離
 ├─ 患者単位または項目単位で暗号化
 └─ 復号鍵を保存しない
          ↓
KMS / Key Vault
 └─ 上位鍵の管理・交換・失効
```

---

## 4. 設計上の優先順位

1. 本人情報と研究データの分離
2. クライアント側暗号化
3. 鍵管理の分離
4. 役割別アクセス制御
5. 監査ログ
6. AI入力最小化
7. 削除・失効設計
8. バックアップと復旧

---

## 5. 禁止事項

- 独自暗号方式の実装
- 鍵のGitHub保存
- データと復号鍵の同居
- 氏名付き生データを外部AIへ丸ごと送信
- 管理者権限による無制限閲覧
- AI出力を人間の確認なく正本化
- ログなしの閲覧・変更
- 削除不能な共有設計

---

## 6. 位置づけ

本原則は、サーバ・クライアント型MVPの後付け項目ではない。

データ構造、API、AI入出力、Reviewer権限、監査、バックアップを設計する前提条件として扱う。

この方針は、今後の実装、仕様判断、レビュー、Handoffで参照する。
