### この結果の意味

検索が「ページトークンを返すのに0件」という挙動を示している。これは、**アカウント内に該当ファイルは存在するが、コネクタの権限スコープが除外している**ことを示す。

すなわちClaudeのDriveコネクタは、いわゆる `drive.file` 相当のスコープで動作している。**アクセスできるのは、Claude自身が作成したファイル、またはユーザーがファイルピッカーで明示的に選択したファイルのみ。**

### したがって、以下の対処は無効

- ❌ フォルダの共有設定を「リンクを知る全員」に変更する → スコープの問題であり共有の問題ではないため無効
- ❌ フォルダを公開にする → 同上。かつ非公開要件に反する
- ❌ Driveリンクを会話に貼る → Claudeはリンクからファイルへ到達できない
- ❌ Claudeに閲覧権限を付与する → 権限は既にアカウント単位で通っている。制約はスコープ

**アークの現状認識「Claude：Driveリンクを直接読めるとは限らず、添付が必要になる可能性が高い」は正しい。** ただし理由が「リンク解釈の限界」ではなく「OAuthスコープ」である点が重要で、この差が対処法を分ける。

## 2. 最大の破綻点：ファイルピッカーは解決策に見えるが、通信バスそのもの

Driveを維持する場合、Claudeが読む唯一の方法は、**ケイがファイルピッカーで対象ファイルを明示的に選択すること**になる。

これは条件4「ケイへ毎回の再整理、再選定、再送を発生させない」に**正面から違反する**。

しかも実態はさらに悪い。

- **ファイル単位**：フォルダを選んでも配下は読めない。1ファイルずつ選択が必要
- **セッション単位**：会話をまたぐと権限が持続しない。次のセッションで再選択
- **AI単位**：Gemini、Grok、ChatGPT各担当にはそれぞれ別の受け渡しが必要

つまり **ファイル数 × セッション数 × AI数** の操作がケイに発生する。

`IACProject Shared Operating Rules` §3 が禁じた「ケイをAI間の通信バスにする」状態に、**別の見た目で戻る**。ピッカーは1タップなので負荷が小さく見えるが、乗算で効いてくる。これが本件で最も危険な経路である。

## 4. 推奨構成

### 前提：非公開の中身を2種類に分ける

現在「非公開」で一括りにされているものは、性質の異なる2つを含んでいる。

| 種別 | 内容 | 必要な保護水準 |
|---|---|---|
| **A：未公開作品** | 黒瀬便本文、ビジュアル、レビュー | 公開前なので出したくない。**検索に載らなければ実害は小さい** |
| **B：真の機密** | 医療データ、実測値、個人情報、実名を含む記録 | **絶対に外へ出さない。例外なし** |

Bは Drive に留め置き、AIへ渡さない。これは議論の対象外とする。

**Aについてのみ、共有方式を設計する。** ここを分けないと、医療データの保護水準を小説の原稿にも適用することになり、レビュー経路が成立しなくなる。

### 推奨：三層構成

```
[層1] GitHub Public リポジトリ（既存 systemlink-yandy-site）
      ├─ 目録（作品ID・版・状態・所在・レビュー接続）
      ├─ レビュー結果（Handoff形式）
      └─ REGISTERED / DELIVERED / ACKNOWLEDGED の状態管理
      ※ 本文・画像は置かない。メタデータのみ

[層2] Secret Gist（本文・テキスト素材）
      ├─ 黒瀬便 第一話本文
      └─ 以降の原稿
      ※ URLを知る者のみ到達可。検索エンジンに載らない
      ※ 層1の目録からURLで参照

[層3] Google Drive（バイナリ・機密）
      ├─ 画像・動画の原本
      └─ 種別B（医療データ等）
      ※ AIへは渡さない。人間側の保管庫として維持
```

### なぜこの構成か

**層1（GitHub Public）**
- Claudeが認証なしで読めることを本セッションで実証済み
- Claude Codeが読み書き可能
- 目録とレビュー結果は本文を含まないため、公開しても作品は流出しない
- **コミットSHAが版識別子になる**。これが後述の版管理を成立させる

**層2（Secret Gist）**
- `raw.githubusercontent.com` 経由でURL直読みが可能。**Claudeが認証なしで読める**
- 検索インデックスに載らない
- Git履歴が付くため版管理が効く
- 無料

**⚠️ 重要なリスク：Secret Gist は「非公開」ではなく「非掲載」である。** URLを知っている者は誰でも読める。パスワードもアクセス制御もない。したがって：
- 種別B（医療・個人情報）は**絶対に置かない**
- URLを公開の場（X、LinkedIn等）に貼らない
- 流出時の被害は「未公開作品の先行公開」に限定される、という前提で採否を判断すること

この判断はケイのものであり、Claudeが決めるものではない。**採用しない場合の代替は §6 に記す。**

**層3（Drive）**
- 現在の書庫を捨てない（条件8を満たす）
- バイナリと機密の置き場として役割を限定する
- AIのレビュー経路からは外す

## 5. 版管理とレビュー結果の接続

### Driveの版管理では不十分な理由

Driveにも版履歴はある。しかし**版を外部から指定して取得できない**。

「第3版をレビューしてください」とHandoffに書いても、受け取ったAIが第3版そのものを取得する手段がない。結果として「どの版をレビューしたのか」が確定しない。レビュー結果と対象の対応が壊れる。

**Gitのコミットハッシュは、外部から指定可能な版識別子である。** これが決定的な差になる。

### 推奨する目録形式

層1に、作品ごとに1ファイル。

```markdown
# WORK-TSUZURI-001

**作品名**：黒瀬便 第一話「404号室の置き配」
**担当**：綴
**種別**：A（未公開作品）

## 版

| 版 | 日付 | 所在 | 版識別子 | 状態 |
|---|---|---|---|---|
| v0.1 | 2026-08-06 | gist: <URL> | <commit SHA> | ACKNOWLEDGED |
| v0.2 | | | | REGISTERED |

## レビュー接続

| 版識別子 | レビュアー | レビュー所在 | 状態 |
|---|---|---|---|
| <SHA v0.1> | Claude | inbox/from_claude/2026-08-06_..._review.md | ACKNOWLEDGED |
| <SHA v0.1> | Gemini | inbox/from_gemini/... | DELIVERED |

## 素材（バイナリ）

| 種別 | 所在 | 備考 |
|---|---|---|
| 代表ビジュアル | Drive | AIレビュー対象外 |
```

**状態の定義**（アークの条件6に対応）

- **REGISTERED**：目録に登録された。まだ渡していない
- **DELIVERED**：レビュアーが到達可能な状態になった（層2にURLがあり、目録に記載済み）
- **ACKNOWLEDGED**：レビュー結果が inbox へ返却され、版識別子と紐付いた

**この3状態は層1（GitHub）に置くこと。** Driveに置くと、状態を読めないAIが発生し、状態管理そのものが機能しない。

## 6. 技術的に不可能な部分と代替案（推測で埋めない）

| 要求 | 可否 | 代替 |
|---|---|---|
| ClaudeがDriveフォルダを直接読む | **不可**（実測） | 層2経由、またはClaude Codeによる中継 |
| Claudeが GitHub Private を読む | **不可**（認証情報なし） | Claude Codeが読んで層1へ転記 |
| Claudeが GitHub へ書き込む | **不可**（認証情報なし） | 従来どおり `inbox/from_claude/` へ提案を出し、アークまたはClaude Codeが登録 |
| **Claudeが動画をレビューする** | **不可** | 静止画コンテ＋台本テキストへ分解して渡す。動画そのもののレビューは断念する |
| Claudeが Drive上の画像を読む | **不可** | 会話への直接添付（本セッションで綴の素材は添付経由で読めている）。または層2にBase64は非推奨（容量） |
| Gemini/Grok/ChatGPT各担当の到達可否 | **Claudeには検証不能** | 各AIが自環境で実測して返すこと |

**動画の件は特に明示しておく。** 現時点でIACProjectのAIメンバーのうち、動画作品を内容としてレビューできる者はいない。動画を含むポートフォリオのレビュー経路を設計しても、レビュアーが存在しない。**動画は「レビュー対象外」として目録に明記し、静止画と台本で代替する**のが現実的。

### Secret Gist を採用しない場合の代替

ケイが「URLを知れば誰でも読める」を許容しない場合、選択肢は以下に狭まる。

**代替1：GitHub Private + Claude Code中継**
- 原本はPrivateリポジトリ
- Claude Codeが読み取り、レビュー対象の本文を会話へ提示、またはClaudeが読める場所へ一時展開
- **リスク**：Claude Codeが単一障害点になる。Claude Codeが止まるとClaudeのレビュー経路が全滅
- ケイの操作：0回（Claude Codeへの依頼のみ）

**代替2：レビュー時のみ添付**
- 現状の運用。本セッションの黒瀬便レビューはこの方式で成立した
- **リスク**：ケイの操作が発生する。ただし「レビュー依頼時に1回」であり、常時ではない
- 頻度が低ければ許容範囲。**高頻度になった時点で通信バス化する**

**推奨順**：Secret Gist ＞ 代替1 ＞ 代替2。ただし種別の切り分け（§4前提）が済んでいることが条件。

## 7. 最小検証手順

設計の採否より先に、**1ファイルで経路が通るかを確認する**ことを推奨する。

1. 黒瀬便第一話の本文のみを Secret Gist として作成する（画像は含めない）
2. 生成された raw URL を、層1（GitHub Public）の目録ファイルに記載する
3. アークがその目録ファイルをリポジトリへ登録する
4. **次回のClaudeセッションで、目録ファイルのパスだけを伝える**
5. Claudeが目録→本文まで到達できるかを確認する

**成功条件**：ケイの操作が「目録のパスを1回伝える」のみで、本文へ到達できること。
**失敗条件**：ケイに追加の添付・選択・説明が発生すること。

この検証は1作品・1ファイルで済み、失敗しても損失がない。**全体設計を確定させる前にこれを回すこと**を強く推奨する。

## 8. アークへの指摘（独立レビューとして）

### 指摘1：設計順序が逆転している

Handoff §1 では、Driveに書庫を作成した**後で**、各AIの閲覧能力が異なることが問題として現れている。

保管先を先に決めて、読める者を後から探す順序になっている。本来は逆で、**全消費者が到達できる形式を先に確定し、それに合う保管先を選ぶ**。

今回はまだ投入が2点（本文・ビジュアル）なので、やり直しの損失は小さい。今のうちに順序を戻すのが安い。

### 指摘2：アークが検証できない対象を設計している

Handoff §2 に「アーク：現在、Driveを直接閲覧・保存できない」と明記されている。

つまりアークは、**自分が中身を確認できない書庫について、共有方式を設計している**。目録と実体の乖離を検出する手段がない。

`2026-08-06_CLAUDE_CODE_TO_KAKEZUKI_SIMILAR_EPISODES_SCOPE_DONE.md` で報告された「コードとドキュメントが4日間食い違っていた」件と同型の構造である。**記録者が実体を確認できない状態は、乖離を必ず生む。**

推奨：アークが到達できる場所（GitHub）を原本とし、到達できない場所（Drive）は原本にしない。

### 指摘3：依頼が制約不足で、3案が発散する

現在の依頼は「改善案を出せ」であり、解の形が制約されていない。Claude・Gemini・Grokは環境が異なるため、**それぞれ自環境に最適化した互換性のない3案**を返す可能性が高い。その後アークが §6 で「重複、矛盾、実現可能性を整理」して1〜2案へ圧縮する工程が、そのぶん重くなる。

推奨：制約を1つ追加して再送する。

> **必須制約**：採用案は、レビュー1件あたりのケイの操作が0回であること。ケイの選択・添付・説明を要する案は提出しない。

この1行があれば、Driveピッカー方式は自動的に脱落し、3案の発散幅がかなり狭まる。

### 指摘4（別件・再掲）

`AI_MEMBER_DIRECTORY.md` に**「纏めの君」が未記載**。日次の外部動向調査、モデル提供停止時のリスク管理、文献追跡を担当しているが、ディレクトリに載っていないため他AIが担当を把握できない。追記を依頼する。
