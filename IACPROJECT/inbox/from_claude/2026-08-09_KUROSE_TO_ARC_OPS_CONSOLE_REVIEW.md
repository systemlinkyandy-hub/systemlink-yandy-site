## 1. 致命的な指摘：稼働環境の前提が実態と食い違っている

**これが最大の問題である。**

要件は「ローカルデスクトップアプリ（PySide6）」を第一候補としている。しかし：

- **ケイの常用環境はスマートフォン（Android / Termux）である**
- **PC（Surface / デスクトップ）の起動は不定期であり、余力があるときのみである**

つまり本アプリは、**ケイが最も長時間過ごす環境では動作しない。**

「人間がAI間通信のルーターになる状態を解消する」という第一目的に照らすと、これは重大な矛盾である。ルーター役を強いられているのは主にスマートフォン運用中であり、そこをカバーできないアプリは、目的の中心部分を解決しない。

### 必須要件の追加

デスクトップアプリという方針自体は維持してよい。ただし以下を**MVPの必須要件**とする。

> **生成した起床パケット・集約結果は、ケイがスマートフォンから参照できる形で出力すること。**
>
> 具体的には、GitHubリポジトリ内のファイルとして書き出す、またはGmail送信するなど、PCを離れても内容にアクセスできる経路を必ず持つこと。

これがないと、パケットがPC内に閉じ込められ、スマートフォン運用時に何の役にも立たない。

## 4. 過剰要件（MVPから除外）

### §1 Dashboard（8状態の可視化）── 除外

理由：状態表示の正確性は、**全AIが自分の状態を正しく申告すること**に依存する。実際にはそうならない。

現に `CURRENT_PENDING` を見れば分かるとおり、黒瀬自身のpendingが2件残ったまま数日経過している（ACKは作成済みだが配送されていない）。**ダッシュボードは、この状態を「未処理2件」と表示し続ける。**

不正確なダッシュボードは、無いより悪い。ケイが表示を信頼して判断すると、実態とずれた判断になる。

MVPでは `CURRENT_PENDING.md` の**素の内容を整形表示するだけ**でよい。状態推論を持たせない。

### §3 Next AI判定 ── 除外

理由：**ここが「中央司令塔にしない」という設計原則の唯一の破れ口である。**

要件は「提示する」と書いており、決定はしない建付けになっている。しかし、**提示が常に出続ければ、ケイはそれに従う。** 実質的にルーティング権限がツール側へ移る。

さらに `Design Principle` は「アークが研究判断・仕様判断を代行する構造にはしない」と明記している。次担当の決定は運用判断であり、この原則と整合しない。

MVPでは、Handoffに書かれた `To` と `Required next action` を**そのまま転記して表示するだけ**にすること。推論を加えない。

### §8 18:00制御 ── 除外（ただし別途対応）

理由2点。

1. **既存の正本と数値が食い違っている。** `06_DAILY_OPERATION` では平日16:30に終了Checkpoint、17:00終了と定められている。本要件の18:00はどこから来た数値か不明。**正本と異なる時刻をアプリに実装すると、アプリが正本を上書きする。**
2. より重要な点として、`IAC-OPS-COST-REDUCTION-001` 案5は「**AI側が受けない**」方式を提案している。ケイの操作を制限するのではなく、AIが着手を拒否する形である。アプリによる時刻制御は、ケイ側を止める設計であり、思想が異なる。

時間制御は**アプリの機能ではなく運用ルールとして**扱うこと。

## 5. 承認する範囲（MVP確定版）

以下**3機能のみ**をMVPとする。

### A. Handoff Inbox（読み取り専用）

- GitHubからHandoff一覧を取得
- From / To / Cc / Task ID / Date / Required next action / Questions queue / path を抽出して表示
- 必須項目の欠落を警告表示

**書き込みは行わない。**

### B. 起床パケット生成

各AI向けに、以下を1ファイルにまとめて出力する。

- 共通起床文
- 最新commit hash
- 対象Handoffの本文またはパス
- 必要な運用ルールへの参照

**§1の必須要件により、出力先はスマートフォンから参照可能な場所とすること**（リポジトリ内ファイル、またはGmail送信）。

これが**本アプリの中核価値**である。ケイが複数資料を探して組み立てる作業をなくす。ここだけでも実装されれば投資に見合う。

### C. Questions Queue 集約

- 各Handoffから Questions queue を抽出
- 同一・類似の質問をまとめる
- **ケイへの確認事項を1画面に集約する**

`IACProject_AI_Onboarding` §5 の「ケイの確認事項は最大2件」「質問はCheckpointでまとめて確認する」という既存ルールと完全に整合する。**これは要件の中で最も原則に忠実な機能である。**

## 6. 追加すべき要件（欠落）

### 6-1. パース失敗時の挙動

Handoffのフォーマットは、AIごとに揺れている（実際に `# HANDOFF` 形式と `# HANDOFF PACKET` 形式が混在している）。**パーサは必ず失敗する。**

**失敗時にアプリが停止してはならない。** 抽出できなかった項目は空欄として表示し、警告を出したうえで処理を続行すること。エラーで止まると、ケイが原因調査に入ることになり、目的と正反対の結果になる。

### 6-2. 保守負荷の見積り

本アプリが壊れた場合、**ケイの運用が止まる。**

MVPを3機能に絞る理由の一つはこれである。機能が少ないほど壊れにくく、壊れたときに切り分けやすい。

「アプリが壊れているときは、従来どおり手動で運用する」という**フォールバック手順を、実装と同時に文書化すること。**

## 8. Technical Direction について

Python / PySide6 という選択に異議はない。ただし §1 の必須要件（スマートフォンからの参照経路）を満たすこと。

**なお、GUIが本当に必要かは再検討の余地がある。** MVPの3機能は、いずれも「入力を受けて、ファイルを出力する」処理であり、CLIでも成立する。既存の `iac-deliver` もCLIである。

GUI実装は工数が大きく、かつ**ケイがPCを起動しないと使えない**。CLIであれば Termux からも実行できる可能性がある。

**技術選択はClaude Code Fableの判断に委ねるが、「GUIありき」で進めないこと。** MVPの3機能をCLIで実装し、必要と判断された時点でGUIを載せる順序を推奨する。
