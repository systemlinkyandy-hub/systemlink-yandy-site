# Handoff: Dropbox Basic 導入可否レビュー依頼

From: 田中
To: スネーク / 二葉 / 黒瀬 / アーク
Date: 2026-08-13 JST
State: 評価依頼

## 背景

Dropboxから一般案内メールが届いている。現時点では有料契約を示す情報は確認できておらず、無料のDropbox Basicを補助インフラとして使う価値があるかを検討したい。

GitHub内を検索した範囲では、既存IACProjectにDropboxを前提とした設計は見つかっていない。

## 想定用途

候補は以下。

1. GitHubに置きたくない大きめバイナリの一時保管
   - 動画素材
   - 画像
   - PDF
   - ログ

2. SharedBrain / Obsidian原資料のバックアップ候補
   - お父さんの設計書・技術メモのスキャン原本
   - Git管理に向かない画像・PDF等

3. ミニPC・スマホ・PC間の軽い同期
   - 厳密な版管理が不要な作業素材

## 境界

Dropboxを以下には使わない前提。

- APIキー
- トークン
- 秘密鍵
- その他シークレット

シークレットはGitHub Secrets、ローカル.env、将来的なSecret Manager等で扱う。

## 暫定アーキテクチャ案

- GitHub = 正本 / 履歴 / Handoff / コード
- Dropbox = 大きいバイナリ / 原資料 / 補助バックアップ
- Obsidian = Knowledge Layer / 知識構造

Dropboxを基幹インフラにするのではなく、無料枠の範囲で補助レイヤーとして使う案。

## 各担当に確認したいこと

### スネーク
外部サービスとしてのDropbox Basicを、現在の代替候補（Google Drive、OneDrive等）と比べて導入価値があるか。無料枠・将来の制約・ロックイン観点も含めて判定。

### 二葉
現在の知識構造・SharedBrain / Obsidian構想との接続で、Dropboxを原資料レイヤーに置く設計が自然か。メタ情報と実体ファイルの分離案があれば提示。

### 黒瀬
セキュリティ、同期事故、正本の二重化、バックアップと同期の混同などの観点からレビュー。導入する場合の最低限ルールを提示。

### アーク
IACProjectのインフラとして採用する場合の配置、命名、同期対象、GitHubとの境界、将来の自動化余地を評価。導入可否の集約を担当。

## 求める回答形式

- 判定: 導入 / 条件付き導入 / 不採用
- 主理由: 3点以内
- 必須ルール: あれば
- 他サービス優先なら代替案

ケイ本人に再調査・再編集を要求せず、各担当で判断してHandoffを返すこと。
